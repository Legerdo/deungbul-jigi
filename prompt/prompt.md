# Three.js 고품질 2.5D 픽셀 액션 RPG 제작 벤치마크

TypeScript + Three.js + Vite로 브라우저에서 플레이할 수 있는 독창적인 2.5D 픽셀 액션 RPG를 실제 제작하라. 평가 대상은 기능의 개수가 아니라, 직접 제작한 픽셀 아트·애니메이션·3D 공간·조명·게임 필이 하나의 완성된 장면으로 통합되는 수준이다. 계획이나 예제 코드가 아니라 실행 가능한 프로젝트를 완성한다.

## 1. 경험과 범위

5~8분에 완주하는 작은 수제 맵을 만든다. 황혼의 계곡 마을에서 출발해 물안개 낀 숲과 다리를 지나, 폐허의 수호자를 쓰러뜨리고 신전의 등불을 되살린다. 세 구역은 하나의 짧은 동선으로 연결한다. 제목과 캐릭터 디자인은 자유롭게 정하되 모든 사용자용 텍스트는 자연스러운 한국어로 작성한다.

주인공 1명, 짧은 안내를 하는 NPC 1명, 행동과 실루엣이 다른 일반 적 2종, 공격 패턴 2개 이상을 가진 보스 1체를 구현한다. 시작·진행·보스전·승리·사망·재시작이 연결되어야 한다. WASD 이동, 마우스 방향 조준과 좌클릭 공격, Space 회피, E 상호작용을 사용하고 게임 안에서 알려준다.

완주 가능한 게임을 전제로, 추가 작업은 아트와 모션의 완성도 → 공간·조명 통합 → 전투 피드백 → 콘텐츠 양 순으로 투자한다. 인벤토리·제작·스킬트리·절차적 월드·멀티플레이는 범위에 넣지 않는다.

## 2. 아트 디렉션

목표 화면은 ‘픽셀 캐릭터가 실제로 살아가는 작은 입체 디오라마’다. 따뜻한 창문과 석등, 차가운 물안개, 낡은 돌과 목재의 질감, 전경의 가지와 먼 절벽을 조합한다. 따뜻한 마을에서 차가운 폐허로 분위기가 변하고, 승리 시 되살아난 빛으로 시각적 보상을 준다. 첫 플레이 화면부터 이 방향이 드러나야 한다.

- 픽셀 아트: 제한된 팔레트, 의도적인 픽셀 덩어리와 명암, 읽기 쉬운 실루엣을 사용한다. 캐릭터·적·주요 소품은 식별 가능한 고유 디자인을 갖는다. 단순 도형 placeholder나 고해상도 이미지를 무작정 축소한 노이즈로 대신하지 않는다.
- 3D 공간: 지형·건축물·다리에는 실제 높이와 부피를 부여한다. 플레이어가 계단이나 경사로를 오르고 물 위의 다리를 건너며, 나무·기둥의 앞뒤를 지날 수 있어야 한다. 충돌·발 위치·가림이 보이는 공간과 일치해야 한다.
- 조명 통합: 환경의 빛·안개와 캐릭터의 밝기·색감·접지 그림자를 일치시킨다. 캐릭터가 화면 위에 붙인 스티커처럼 보이지 않게 한다. 움직이는 물, 바람에 반응하는 식생, 소수의 분위기 입자로 정적인 배경을 피한다.
- 구도: 전경·중경·후경을 구분하고 캐릭터와 적의 공격을 쉽게 읽을 수 있게 한다. 사선 직교 또는 완만한 원근 카메라 중 적합한 것을 선택한다. 추적과 짧은 연출을 지원하되 불필요한 회전·줌·흔들림으로 판독성을 해치지 않는다.

Bloom·DOF·빛줄기·반사·커스텀 셰이더는 미술적 효과가 분명할 때 선택한다. 효과를 모두 넣을 필요는 없다. 후처리를 꺼도 기본 아트와 구도가 성립해야 하며, 과도한 발광이나 블러로 부족한 디테일을 가리지 않는다.

## 3. 픽셀 애니메이션과 게임 필

주인공은 최소 4방향 표현과 대기·이동·공격·회피·피격·사망 동작을 갖는다. 좌우 미러링은 허용하지만 앞뒤는 구분한다. 실제 포즈와 실루엣이 변하는 프레임 애니메이션을 만들고, 한 장의 그림을 이동·회전·확대하는 것만으로 모든 동작을 대신하지 않는다. 적과 보스도 공격 예고·공격·피격·사망이 시각적으로 구분되어야 한다.

원본 픽셀 해상도와 프레임 수는 화면상 크기와 동작에 맞게 결정한다. 프레임마다 캐릭터 크기와 발 기준점을 유지하고, 무기·망토가 잘리지 않도록 동일한 캔버스에 충분한 여백을 둔다. 픽셀 원본의 밀도는 일관되게 유지하되 3D 원근에 따른 화면상 크기 변화는 허용한다.

공격은 준비 → 타격 → 회수의 리듬을 갖고, 피격 순간에는 짧은 hit-stop·방향성 스파크·적의 반동·절제된 카메라 충격·효과음을 맞물리게 한다. 강한 공격은 예고와 충격의 크기로 구별한다. 회피는 입력 즉시 읽히고, 공격 판정과 회피 가능 시점은 보이는 동작과 일치해야 한다. 소리를 꺼도 명중·피격·위험을 구분할 수 있어야 한다.

픽셀 스프라이트는 선명하게 표시하고, 카메라 이동 중 눈에 띄는 떨림·잔상·프레임 튐·발 미끄러짐을 수정한다. 텍스처 확대와 축소 정책은 구분해 결정한다. 화면 전체를 픽셀화하는 필터로 원본 픽셀 아트 제작을 대신하지 않는다.

## 4. 모션 연출·UI·사운드

시작에는 스킵 가능한 짧은 카메라·타이틀 연출을, 보스 진입에는 환경 변화·보스 동작·이름 표시를 결합한 짧은 연출을 만든다. 승리 시 빛과 환경의 변화로 여정을 마무리한다. 개별 효과를 나열하기보다 각 장면에 시작·강조·마무리의 리듬을 부여한다.

HUD는 체력·현재 목표·필요할 때의 보스 체력만 작게 표시한다. 메뉴·사망·승리 화면까지 같은 미술 방향을 유지하고 버튼에 명확한 입력 피드백을 준다. 게임 화면을 웹 대시보드 카드나 장문의 설명으로 덮지 않는다.

공격·피격·회피·보스 공격·UI 효과음과 간단한 환경음을 구현한다. Web Audio 합성은 허용한다. 오디오는 사용자의 시작 입력 이후 활성화하고 음소거를 제공한다.

## 5. 제작 조건

이 모델 자체의 제작 역량을 평가하므로 시각 에셋은 직접 작성한 코드·픽셀 데이터·셰이더로 제작한다. 외부 이미지/영상 생성 모델, 완성형 게임 에셋팩, 기존 게임 구현을 가져와 해결하지 않는다. 개발 라이브러리·공식 문서·오픈 라이선스 한글 폰트는 사용할 수 있다.

에셋은 프로젝트 안에서 재생성할 수 있도록 생성 코드와 필요한 시드를 남긴다. Three.js를 핵심 렌더러로 사용하며, 환경은 코드로 구성해도 된다. GLB 내보내기나 별도의 모델링 파이프라인은 요구하지 않는다. 게임 상태·렌더링·UI의 책임은 나누되 별도 범용 엔진을 구축하지 않는다.

Windows 11의 일반적인 Node.js 환경에서 설치·개발 실행·타입 검사·프로덕션 빌드가 가능하도록 npm 명령과 lockfile을 제공한다. 기존 프로젝트 지침과 사용자 파일을 먼저 확인하고 보존한다. 백엔드·인증·유료 서비스·배포는 필요 없다.

## 6. 진행 방식

작업 방향과 순서를 짧게 정한 뒤 구현한다. 먼저 대표 장면 하나에서 최종 스타일의 캐릭터·환경·조명과 이동·적 하나의 전투를 함께 완성하고, 그 기준을 나머지 동선과 보스로 확장한다. 모든 구역을 임시 그래픽으로 늘어놓은 뒤 마지막에 아트를 교체하는 방식은 피한다.

미완료 항목과 장애물은 짧은 체크리스트로 관리한다. 다음 작업이 가능하면 중간 보고에서 멈추지 말고 수행한다. 통과한 항목을 변경도 없이 반복 검증하거나, 검증만을 위한 다중 에이전트 체계를 추가하지 않는다. 결함이 발견되면 해당 부분과 영향받는 경로를 수정·재검증한다.

## 7. 완료 기준과 증거

아래 기준을 실제 실행 결과로 확인한다. 기능 통과와 시각적 품질을 구분해 보고하며, 빌드 성공을 아트 품질의 증거로 취급하지 않는다.

1. 실행: 타입 검사와 프로덕션 빌드가 통과하고, 브라우저에서 시작 → 탐색·전투 → 보스 처치 → 승리 → 재시작을 정상 입력으로 완주한다. 사망 후 재시작도 확인한다. 진행을 막는 오류, 누락 에셋, 처리되지 않은 런타임 오류를 해결한다. 테스트용 순간이동이나 자동 승리만으로 완주를 판정하지 않는다.
2. 시각: 실제 게임에서 마을·숲 전투·보스전 스크린샷을 저장하고 직접 열어 확인한다. 캐릭터 판독성, 공간 깊이, 접지감, 가림 순서, 픽셀 선명도, UI 간섭을 점검한다. 주인공 스프라이트 시트도 원본 크기와 정수배 확대로 확인한다.
3. 모션: 실제 렌더링의 영상 또는 연속 프레임으로 이동·방향 전환·공격·회피·전경 뒤 통과를 확인한다. 정지 스크린샷만으로 모션이 자연스럽다고 판정하지 않는다.
4. 성능: 데스크톱 Chrome의 1920×1080, DPR 1에서 60 FPS를 목표로 한다. 워밍업 후 30초 전투 구간의 측정 환경·렌더링 해상도·평균 FPS·p95 프레임 시간을 기록한다. 하드웨어 가속 여부를 구분하고, 측정하지 않은 수치는 추정해 적지 않는다.

최종 제출물은 실행 가능한 소스·에셋 생성 코드·README·검증 증거다. README에 실행 명령, 조작법, 검증 결과, 알려진 결함과 미검증 항목을 적는다. 브라우저나 시각 검증 도구를 사용할 수 없으면 가능한 검사를 마친 뒤 무엇을 확인하지 못했는지 명시한다.

필수 기능과 위 품질 기준을 충족하면 제출한다. 충족하지 못한 부분은 구체적으로 밝히며, 미완료 기능을 완료 처리하거나 근거 없이 ‘상용 수준’이라고 평가하지 않는다.
